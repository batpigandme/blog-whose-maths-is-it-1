## Notes on the table

- Downloads are calendar-year counts from api.npmjs.org's point endpoint, 1 January to 31 December of the year named, with no errors. jsbi's count for 2017 is 0; its first publish came after that.
- npm's download counts include installs of a package as another package's dependency. Dependents weren't queried, so how much of any count is that isn't known. That applies to every row. Two 2023 counts, bn.js's (1.95 billion) and big.js's (1.03 billion), are far above the others, and the reason wasn't investigated.
- Stars and latest versions are as of 2026-11-19. They aren't the 2017 to 2023 values; only the downloads are for those years.
- The repository column gives the commit that was the default branch's HEAD on 2026-11-19, and last commit is that commit's committer date. The two don't always agree with other dates GitHub or npm gives:
  - jstat: the default branch is 1.x, and the repository's `pushed_at` (2026-02-28) is later than the last default-branch commit (2022-12-28).
  - numeric: `pushed_at` is 2018-09-14, and the last default-branch commit is 2012-12-20, the same day as its latest npm version, 1.2.6. Its README doesn't say it is unmaintained.
  - decimal.js: the last commit is 2026-08-30, and its latest npm version is from 2025-07-06.
  - ndarray's README carries a "stable/frozen" badge image (stability-badges `frozen.svg`).
- The READMEs read at these commits aren't kept in this folder. The sentences quoted below are from them, and each can be checked at the pinned commit.

## Two README passages, verbatim

JSBI, GoogleChromeLabs/jsbi at 5382367c7e3199858d36bb620977e1f90605bcb9, README.md, section "Why?":

> JSBI is designed for exactly this purpose: it provides a BigInt “polyfill” implementation that behaves exactly like the upcoming native BigInts, but with a syntax that you can ship on all browsers, today.

> it behaves exactly like native BigInts do where they are available, so to eventually migrate to those, you can [mechanically](https://github.com/GoogleChromeLabs/babel-plugin-transform-jsbi-to-bigint) update your code’s syntax; no re-thinking of its logic will be required.

> The solution is to do it the other way round: write code using a library’s syntax, and [transpile it to native BigInt code](https://github.com/GoogleChromeLabs/babel-plugin-transform-jsbi-to-bigint) when available.

In "Installation/Usage", the same README says: "Use [babel-plugin-transform-jsbi-to-bigint](https://github.com/GoogleChromeLabs/babel-plugin-transform-jsbi-to-bigint) to transpile JSBI code into native BigInt code." The curly quotes around "polyfill" are the README's own.

BigInteger.js, peterolson/BigInteger.js at 441f6bd73cef6a5029dd5600f17e3dd79eafeddb, README.md, "Update (December 2, 2018)":

> `BigInt` is being added as a native feature of JavaScript. This library now works as a polyfill: if the environment supports the native `BigInt`, this library acts as a thin wrapper over the native implementation.
